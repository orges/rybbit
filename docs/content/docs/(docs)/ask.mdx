title: Ask
description: Ask questions about your analytics in plain language and get answers grounded in your data
---

Ask is a chat inside Rybbit that reads your data and answers questions about it. Open it from **Product Analytics → Ask** in the sidebar.

It is not a generic chatbot with your numbers pasted in. Every figure it shows comes from a tool call against the Site you are asking about, and the call is shown to you: what was asked, how long it took and what came back. If it cannot see something, it tells you instead of guessing.

Goals are part of that. Ask about a target — "am I on track for the signup goal?" — and it reads the goals configured on the Site, their conversion rate over the range, and whether that rate is rising or falling. Goals hold a condition rather than a number, so it reports the rate and the direction, and never claims a goal is met.

## Asking questions

Type a question in the composer and press Enter (Shift+Enter for a new line). Threads are saved per user and per Site, so you can start an investigation, leave it, and pick it up later from the rail on the left.

Ask understands the range you are looking at. Ask while the dashboard is on "Last 7 days" and "how are we trending" means the last 7 days. When you name a period yourself — "yesterday", "last week", "the 30th" — it uses that instead, including in a Site's timezone.

Filters in the dashboard apply to the question too, and the answer records which filters were in effect, so a surprising number can always be traced back to the view it came from.

Questions it can answer well:

- "How is traffic trending compared to the previous period?"
- "Which pages get the most views but the worst bounce rate?"
- "What are the top custom events today, and did any of them start this week?"
- "Where did we lose people in the signup funnel?"
- "Show me sessions where people hit a 500 error, longest first."
- "What is our day-7 retention?"
- "How are my goals doing, and which one is falling?"

It can also write SQL when no structured tool fits, over a read-only view of your own events.

## What it shows

Answers arrive as you watch them being written, with the model's reasoning and every tool call listed above the text. Tables and charts are rendered from the query results, not described: pick the column that labels each point and the number to plot, and the chart is drawn with the same components as the rest of Rybbit.

A retention answer is drawn as the Retention page draws it, one line per cohort. A funnel is drawn as the Funnels page draws it: step order, conversion from the previous step, drop-off, and the sessions behind each step, expandable in place. Both link to the page they came from, so you can keep working there.

An error answer goes all the way to the recording. Ask what the top errors are, or what one specific error did to real people, and you get the sessions each occurrence happened in — every `session_id` opens that recording in Replay, at the moment the error fired rather than at the start of the session.

Under each answer you can copy it, or retry it with the same question. Retrying replaces the previous answer rather than adding a second one.

To ask a different question from the same point, hover one of your own questions and click the pencil. It comes back to the composer, and sending it replaces that question and every answer after it — so a wrong assumption three questions back is fixed in one edit rather than by starting a new thread. Editing the first question renames the thread to match.

Any figure in an answer that is not in the tool results is listed under it. Usually that is the model's own arithmetic, but it is flagged rather than passed off as data.

## Teaching it about your site

Some context is not in the data: what a "signup" means internally, which campaign matters, which outage you are still explaining. Send `/remember` followed by a note and it is included in every future question on that Site.

```
/remember Signups are the demo_request event, not the signup button click
```

Run `/usage` in any thread to see how many tokens that conversation has used.

## What leaves your instance

Enabling Ask sends data to whichever model endpoint you configure. This is worth reading before you turn it on, particularly if you self-host Rybbit to keep visitor data on your own infrastructure.

Sent to the model on every question:

- **Your question, and the conversation around it** — the last 20 turns of the thread.
- **Project memory** — everything added with `/remember`, on every question, for every thread on that Site.
- **Rows from your analytics**, including page titles, URLs, referrers, custom event names and event property values. These are stripped of control characters, not of content.
- **The Site's name** and the dashboard filters in effect when you asked.
- **A structural summary of individual sessions**, if you ask what a visitor did: the pages they visited with time on each, what they clicked and how often, which form fields they touched, whether a form was submitted, and error messages.

Not sent: session replay recordings, the contents of the page, anything a visitor typed, copied text, or anything belonging to another Site or organization. The session summary cannot include typed input — Rybbit's tracker records the field a visitor touched, never what was in it — so that is a property of the data rather than something filtered on the way out. Replay recordings themselves are never read.

Every tool is read-only and bound to the one Site you are asking about, and Ask cannot write, save or delete anything.

The trade is that the analysis happens wherever the model runs. If that matters — and for visitor-level strings it often does — point `OPENROUTER_API_URL` at a gateway you control. `OPENROUTER_API_URL`, `OPENROUTER_MODEL` and `OPENROUTER_API_KEY` are all it takes; there is no separate privacy mode to configure.

## Reading what visitors did

Ask can summarise a session as structure: pages in order with time on each, clicks grouped by control, which form fields were touched, whether the form was submitted, errors, outbound links. Give it a session id and it will read one; give it several and it reports only what they share — the page where they stopped, controls that led nowhere, forms touched but never submitted, errors that repeat.

It finds them the way the Sessions page does, so *"which sessions visited /pricing and then left"* is a question it can answer before it reads anything. Filters use the same parameters the filter bar offers — page, event, country, device, browser and the rest.

This is the interaction events your tracker already records, reduced to a summary. It is **not** session replay: no recording is read, no page content is, and nothing a visitor typed is available to it — the tracker never records it, so Ask cannot report what was in a field and will say so if asked.

It follows the **session replay** setting in Site Settings, so it is available on a Site only where you already keep session recordings. It costs no extra storage and does not change what is recorded.

## What is stored

Questions, answers, the tool trail and any `/remember` notes are kept in your Postgres so threads survive a restart, and they stay until you delete the thread. There is no automatic expiry. Deleting a user, organization or Site removes them by cascade.

## Configuration

Ask is off until an OpenAI-compatible chat completions endpoint is configured. Set these in `.env` and restart:

```bash
# Any OpenAI-compatible endpoint. Leave OPENROUTER_API_URL unset to use OpenRouter.
OPENROUTER_API_URL=http://your-gateway:8317/v1/chat/completions
OPENROUTER_MODEL=your-model
OPENROUTER_API_KEY=your-key
OPENROUTER_REASONING_EFFORT=medium
# Tried in order when the primary model is rate-limited or cooling down
OPENROUTER_FALLBACK_MODELS=backup-model-1,backup-model-2
```

The model needs tool calling and streaming. Every answer costs tokens and a few ClickHouse queries; on a busy Site, a long investigation can run a dozen queries.

## Safety

Ask is read-only. It cannot create dashboards, change goals or flags, or modify anything — if you ask, it will say so. It only ever sees Sites your user already has access to, and the custom SQL it can run is restricted to a read-only view of those Sites with a row cap and a time limit.
